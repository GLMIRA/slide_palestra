Segurança da Informação
Proteger a informação  em qualquer forma.
A palavra-chave é informação, não "computador". Ela vive no papel, na fala, na memória e no HD. Cibersegurança é só o pedaço que cuida do meio digital.
Isso não é novo: Cifra de César (~50 a.C.)
Normal:   A B C D E  ...  X Y Z
Chave +3:  D E F G H  ...  A B C
ATACAR  →  
DWDFDU
A chave é o deslocamento (3). Então vem a pergunta: quantas chaves diferentes essa cifra tem?
CIA
Toda a segurança se apoia em três pilares. E a sigla é fácil de lembrar.
Confidentiality
·
Integrity
·
Availability
C
Confidencialidade
Só quem tem permissão vê.
Ameaça: vazamento, interceptação, senha roubada. Defesa: criptografia e controle de acesso.
I
Integridade
A informação não foi adulterada.
Ameaça: mudar o valor de uma transferência, man-in-the-middle. Defesa: hash e validação.
A
Disponibilidade
Acessível quando se precisa.
Ameaça: DoS/DDoS, ransomware, falha de hardware. Defesa: backup, redundância e limite de requisições.

SQL Injection
VULNERÁVEL
# Python sql = "SELECT id FROM usuarios WHERE usuario = '" + usuario + "' AND senha = '" + senha + "'" cursor.execute(sql)
Isso compila, roda e loga o usuário. Cadê o problema?
SQL Injection 
[C] Confidencialidade
CORRIGIDO
# Python
cursor.execute(
"SELECT id FROM usuarios WHERE usuario = ? AND senha = ?"
, (usuario, senha))
O dado vai separado, como parâmetro. Ele nunca vira SQL.
Mesma correção em Java (PreparedStatement + setString) e C# (@param + AddWithValue).
SQL Injection 
VULNERÁVEL
# Python sql = ("SELECT usuario.id FROM usuarios usuario JOIN perfis perfil ON user.id"         " = perfil.usuario_id "        "WHERE u.usuario = '" + usuario + "' AND p.cpf = '" + cpf + "'") cursor.execute(sql)
Essa query decide se você é o dono pra trocar a senha. Cadê a falha?
SQL Injection 
[C] Confidencialidade
CORRIGIDO

cursor.execute(
"SELECT u.id FROM usuarios u JOIN perfis p ON u.id = p.usuario_id "
"WHERE u.usuario = ? AND p.cpf = ?" , (usuario, cpf))
Parametrizar também a checagem de identidade — a mais sensível de todas.
Mesmo padrão em Java e C# (parâmetros nomeados).

Mass Assignment
VULNERÁVEL
# Python for campo, valor in dados_do_formulario.items():     colunas.append(campo + " = ?")     valores.append(valor) cursor.execute("UPDATE usuarios SET " + ", ".join(colunas) + " WHERE id = ?", valores)
Fomulario de usuario {nome, numero_tell, senha} -> isso é oque o usuario Pode Alterar ! O update salva os campos que chegam do formulário. E se eu não usar o formulário padrão?
Mass Assignment
[I] Integridade
CORRIGIDO
# Python PERMITIDOS = {"usuario", "senha", "nome", "cpf"} for campo, valor in dados_do_formulario.items():     if campo not in PERMITIDOS:         continue     colunas.append(campo + " = ?")
Lista branca: só os campos que o cliente PODE editar; ignora o resto.
Senha em texto puro
[C] Confidencialidade
VULNERÁVEL
# Python — cadastro
cursor.execute(
"INSERT INTO usuarios (usuario, senha) VALUES (?, ?)" ,(usuario, senha))
O cadastro e o login funcionam perfeitamente. Então está tudo certo?
Senha em texto puro
[C] Confidencialidade
CORRIGIDO
# Python — pip install bcrypt import bcrypt hash_ = bcrypt.hashpw(senha.encode(), bcrypt.gensalt()) cursor.execute("INSERT INTO usuarios (usuario, senha) VALUES (?, ?)", (usuario, hash_))
Guarde o hash, nunca a senha. Caminho só de ida — efeito avalanche.
Java: jBCrypt · C#: BCrypt.Net. No login, compare com checkpw / Verify.
Open Redirect
VULNERÁVEL
// JavaScript const destino = new URLSearchParams(location.search).get("next"); window.location = destino || "saldo.html";
Um link que começa no meu domínio pode te levar pro site do golpista. Como?
Open Redirect
[I] Integridade
CORRIGIDO
// JavaScript const ok = destino && destino.startsWith("/") && !destino.startsWith("//"); window.location = ok ? destino : "saldo.html";
Só aceitar caminho interno; qualquer destino externo cai no padrão.
Path Traversal / LFI
VULNERÁVEL
# Python caminho = os.path.join(PASTA, arquivo) with open(caminho) as f:     return responder(f.read())
Eu peço um arquivo pelo nome. Você confia no nome que eu mando?
Path Traversal / LFI
[C] Confidencialidade
CORRIGIDO
# Python base = os.path.realpath(PASTA) caminho = os.path.realpath(os.path.join(PASTA, arquivo)) if not caminho.startswith(base + os.sep):     return responder("Arquivo invalido.", 400)
Canonicalize o caminho e garanta que ele fica dentro da pasta base.
Java: normalize() + startsWith · C#: GetFullPath + StartsWith.
Race condition (TOCTOU)
VULNERÁVEL
# Python — comprar um produto cursor.execute("SELECT preco FROM produtos WHERE id = ?", (produto,))  # le o preco cursor.execute("SELECT saldo FROM contas WHERE id = ?", (conta,))  # le o saldo if preco > saldo:  # checa     return responder("Saldo insuficiente.", 400) cursor.execute("UPDATE contas SET saldo = saldo - ? WHERE id = ?", (preco, conta))  # grava
Ler, checar, gravar — três passos. E se duas compras rodarem ao mesmo tempo?
Race condition (TOCTOU)
[I] Integridade
CORRIGIDO
# Python — checa e debita numa tacada so cur = cursor.execute("UPDATE contas SET saldo = saldo - ? "       "WHERE id = ? AND saldo >= ?", (preco, conta, preco)) if cur.rowcount == 0:     return responder("Saldo insuficiente.", 400)
Checar e debitar numa única operação atômica. Sem saldo, rowcount = 0.
+ PRAGMA busy_timeout. Java: executeUpdate()==0 · C#: ExecuteNonQuery()==0.
Exposição de dados via API
VULNERÁVEL
# Python cursor.execute("SELECT id, usuario, senha, admin, nome, cpf FROM usuarios ...") usuarios.append({"id": linha[0], "usuario": linha[1], "senha": linha[2]})
A tela do admin esconde a senha. Então está seguro?
Exposição de dados via API
[C] Confidencialidade
CORRIGIDO
# Python — sem senha, sem admin cursor.execute("SELECT id, usuario, nome, cpf FROM usuarios ...") usuarios.append({"id": linha[0], "usuario": linha[1], "nome": linha[2]})
O back só devolve o necessário. Esconder no front não é proteger.
Mesmo princípio em Java e C#: nunca serializar campos sensíveis.
Ausência de Rate Limit
VULNERÁVEL
# /login e /recuperar-senha # nenhum limite de tentativas # nenhum bloqueio apos N erros
Quantas vezes você pode errar a senha nesse sistema? Infinitas.
Ausência de Rate Limit
[A] Disponibilidade
CORRIGIDO
# Python — ex.: Flask-Limiter @limiter.limit("5/minute")  # no /login # + lockout apos N falhas por IP/usuario
Limite as tentativas + lockout. Fecha o brute force e o flood.
Mesma ideia em Java/C#: contador de tentativas por IP/usuário.

Como vai funcionar
Quem joga
Sozinho, em dupla ou em grupo de até 5. Vejam o que fica melhor pra vocês.
Onde roda
Baixem o projeto e rodem na própria máquina, em localhost.
Qual linguagem
Escolham a que for mais fácil de entender: Python, Java ou C#.
O objetivo
É um banco vulnerável de propósito. A missão: achar, explorar e corrigir as falhas.
Quantas falhas
12 normais + 4 bônus (essas bem escondidas).
Como caçar
Ler o código, abrir o Burp, interceptar request e resposta. Vale tudo.
Corrijam as falhas, montem um relatório de onde achou cada uma. Ganha quem achar e corrigir mais.
Regras do jogo
  • Sem IA com acesso à sua máquina (Claude Code, Codex, Copilot). Perguntar conceito pode; colar o código, não.
  • Sem ferramentas de SAST (SonarQube e afins). O olho é de vocês.
  • Só ataque a SUA cópia, em localhost. Fora do escopo = desclassificado (e é crime).
  • Não altere as tabelas do banco. O conserto é no código.
  • A correção não pode quebrar a app — tem que continuar rodando (valida no scanner).
  • PoC obrigatório: prove como explorou. "Achei" sem prova não conta.
  • Dúvida com o Mira? Pode — mas a resposta vai pra todo mundo. Cuidado com o que perguntar.
  • Sem DoS/DDoS no amiguinho. 🙂
